## 1. GPT-6: 모델 선택과 캐시 적중률을 작업 단위로 측정하기

OpenAI는 9월 22일 GPT-6 Sol과 Luna를 공개했고, 같은 날 GPT-6용 프롬프트 캐시 진단과 대시보드를 소개했습니다. 공식 안내에 따르면 재사용하는 공유 접두사는 30분 창에서 캐시 대상이 될 수 있으며, 대시보드와 진단 도구는 모델·도구·설정·입력 변경 때문에 발생한 캐시 미스를 비교할 수 있게 합니다. 이는 긴 컨텍스트를 쓰는 에이전트에서 모델 이름만 고르는 문제가 아니라, 지시문과 도구 정의를 얼마나 안정적으로 유지하는가의 문제이기도 합니다.

대표 작업을 "짧은 분류", "다단계 수정", "장시간 조사"처럼 나누고, 각 작업에 허용한 모델·최대 비용·성공 기준을 기록합니다. 프롬프트의 자주 바뀌지 않는 지시와 도구 정의는 앞쪽에 두되, 캐시가 맞았다는 사실을 정답의 증거로 취급하지는 않습니다. 배포 전에는 캐시 적중률, 지연 시간, 실제 결과 품질을 같은 평가 세트에서 함께 비교하고, 도구 변경 뒤의 미스는 회귀 신호로 알립니다.

## 2. GitHub Copilot: 기본 검토 수준과 보존 정책을 명시적으로 결정하기

GitHub는 9월 28일부터 Copilot code review의 기본 노력 수준을 Lite에서 Balanced로 바꾸고, GitHub.com·Mobile·cloud agent의 경험과 정책을 하나로 전환한다고 공지했습니다. 기본값을 그대로 쓰는 조직과 저장소에는 Balanced가 적용되며, Lite를 유지하려면 명시적으로 선택해야 합니다. 통합 경험에서는 채팅 데이터 보존 기간도 기존의 28일이 아니라 계정 수명과 맞춰진다고 안내합니다. 따라서 리뷰의 비용·대기 시간뿐 아니라, 대화 데이터와 자동화 결과의 보존 기준도 함께 확인할 변화입니다.

조직과 중요 저장소의 code review effort 설정을 먼저 내보내고, 작은 대표 PR 묶음에서 Lite와 Balanced의 지적 수·유효 지적 비율·검토 완료 시간을 비교합니다. 클라우드 에이전트와 Mobile 사용이 있는 팀은 새 통합 정책의 보존 범위가 내부 데이터 분류와 맞는지 법무·보안 담당자와 확인합니다. "기본값"에 기대지 말고 저장소별 선택, 예외 사유, 재검토 날짜를 정책 문서에 남겨야 다음 모델 전환에도 판단을 재현할 수 있습니다.

## 3. TestFlight 4.4: 테스트 도구의 화면 변화도 릴리스 절차에 포함하기

Apple은 9월 24일 TestFlight 4.4.0을 배포했습니다. iPhone 가로 방향과 macOS의 iPhone Mirroring 환경에서 크기 조절을 지원하며, App Store Connect 3.3도 비슷한 방향·크기 조절과 대규모 팀의 내부 테스터 초대 성능 개선을 포함합니다. 테스트 대상 앱만이 아니라 테스터가 빌드를 찾고 설치하고 피드백을 남기는 도구의 흐름도 변한 셈입니다.

다음 베타 배포에서 iPhone 세로·가로와 Mirroring 사용 여부를 포함한 짧은 테스터 여정을 실행해, 초대 링크·빌드 선택·피드백 진입이 모두 가능한지 확인합니다. 내부 테스터가 많은 팀은 초대 처리 시간을 이전 릴리스와 비교하고, 화면 회전에서만 나타나는 안내 문구나 스크린샷 문제를 별도 항목으로 기록합니다. 다만 도구의 안정성 개선 공지만으로 앱 호환성이 증명되지는 않으므로, 앱의 실제 베타 OS·기기 조합 검증은 계속 분리해 실행합니다.

출처: [Apple Developer: TestFlight 4.4.0](https://developer.apple.com/news/releases/?id=01062025a), [Apple App Store Connect 릴리스 노트](https://developer.apple.com/help/app-store-connect/release-notes/)
