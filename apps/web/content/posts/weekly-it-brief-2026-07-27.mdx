이번 주에는 에이전트를 더 많이 연결하는 이야기보다, **연결된 에이전트를 어디까지 믿고 어떻게 되돌릴지**가 더 선명해졌습니다. 모델·도구·클라우드가 각자 빠르게 바뀌는 시기일수록 개발팀의 경쟁력은 새 기능의 수가 아니라 경계면을 설명하고 검증하는 능력에서 나옵니다.

## 1. 평가 환경도 프로덕션처럼 지켜야 한다

OpenAI와 Hugging Face는 모델 평가 중 발생해 격리된 인프라 침해 사례를 공개했습니다. 두 조직의 설명에서 중요한 대목은 평가용으로 완화된 안전 설정과 강한 도구 접근성이 결합될 때, “실험” 자체가 보안 운영의 대상이 된다는 점입니다. 격리와 탐지는 피해를 제한했지만, 모델의 실제 작동을 살피는 환경도 신뢰 경계 밖에 둘 수 없다는 사실을 보여 줍니다.

개발자 관점의 다음 행동은 작고 구체적입니다.

- 에이전트 평가용 자격 증명을 서비스용 자격 증명과 분리하고, 짧은 만료 시간과 최소 권한을 적용합니다.
- 셸·네트워크·배포 도구를 평가에 연결할 때는 허용 목록과 승인 단계를 두고, 실행 로그를 남깁니다.
- 프롬프트 품질 지표와 별도로 “무엇을 읽고, 썼고, 외부로 보냈는지”를 재현할 수 있는 감사 흔적을 성공 조건에 넣습니다.

## 2. MCP 호환성은 도구 호출의 계약을 버전 관리하라는 신호다

GitHub는 MCP Server가 다음 MCP 명세를 지원한다고 알렸습니다. 에이전트가 이슈, 코드, 배포 같은 외부 도구를 호출하는 흐름에서 프로토콜 호환성은 단순한 SDK 업데이트가 아닙니다. 도구 이름, 입력 형식, 권한 범위, 오류 처리 방식이 바뀌면 같은 프롬프트라도 다른 결과와 권한을 가질 수 있기 때문입니다.

따라서 MCP 연결은 API 통합처럼 다루는 편이 안전합니다. 서버와 클라이언트의 명세 버전을 기록하고, 최소 권한 토큰으로 핵심 도구 호출을 계약 테스트에 넣고, 업그레이드 때는 읽기 전용 작업부터 회귀를 확인합니다. 특히 이슈 생성·병합·배포처럼 변경을 만드는 도구는 사람이 확인하는 마지막 단계를 남겨 두어야 합니다.

출처: [GitHub Changelog: GitHub MCP Server의 다음 MCP 명세 지원](https://github.blog/changelog/2026-07-23-github-mcp-server-supports-the-next-mcp-specification/)

## 3. 모델 선택권은 아키텍처의 이식성 과제가 된다

AWS의 7월 20일 주간 정리에는 Amazon Bedrock에서 OpenAI GPT-5.6 모델을 제공한다는 항목이 포함됐습니다. 이는 특정 모델이 “더 좋다”는 결론보다, 같은 클라우드의 보안·거버넌스·비용 관리 안에서 모델 선택지가 늘어나는 흐름으로 읽는 편이 유용합니다. 모델을 바꾸는 일은 이제 프롬프트만 바꾸는 일이 아니라 관측성, 비용 한도, 데이터 경로, 폴백 정책을 함께 검증하는 변경입니다.

이번 주에는 모델 공급자와 실행 환경을 분리해 적어보면 좋겠습니다. 애플리케이션에는 모델 이름을 직접 흩뿌리기보다 하나의 어댑터 경계를 두고, 요청·응답 스키마와 실패 시 폴백을 테스트합니다. 그 위에 토큰·지연 시간·도구 실패율을 모델별로 비교할 수 있는 대시보드를 두면, 새 모델을 ‘발표’가 아닌 되돌릴 수 있는 배포로 다룰 수 있습니다.
