이번 주에는 에이전트를 더 많이 연결하는 것보다 **어디까지 신뢰하고, 실행 결과를 어떻게 되돌릴지**가 중요하게 다뤄졌습니다. 모델과 도구, 클라우드가 빠르게 바뀔수록 개발팀은 새 기능을 추가하는 데 그치지 않고 각 요소의 역할과 한계를 설명하고 검증해야 합니다.

## 1. 평가 환경도 실서비스처럼 보호해야 한다

OpenAI와 Hugging Face는 모델 평가 도중 격리된 인프라가 침해된 사례를 공개했습니다. 평가 과정에서 보안 설정을 완화하고 강력한 도구 접근 권한을 함께 제공하면, 실험 환경도 보호 대상이 됩니다. 격리와 탐지로 피해를 제한했지만, 모델을 시험하는 환경도 안전하다고 가정할 수는 없습니다.

개발자 관점의 다음 행동은 작고 구체적입니다.

- 에이전트 평가용 자격 증명을 서비스용 자격 증명과 분리하고, 짧은 만료 시간과 최소 권한을 적용합니다.
- 셸·네트워크·배포 도구를 평가에 연결할 때는 허용 목록과 승인 단계를 두고, 실행 로그를 남깁니다.
- 프롬프트 품질 지표와 별도로 “무엇을 읽고, 쓰고, 외부로 보냈는지”를 확인할 수 있는 기록도 성공 조건에 포함합니다.

출처: [OpenAI와 Hugging Face의 모델 평가 보안 사고 설명](https://openai.com/index/hugging-face-model-evaluation-security-incident/)

## 2. MCP 호환성에 맞춰 도구 사용 방식도 관리해야 한다

GitHub는 MCP Server가 다음 MCP 명세를 지원한다고 알렸습니다. 에이전트가 이슈, 코드, 배포 같은 외부 도구를 호출하는 흐름에서 프로토콜 호환성은 단순한 SDK 업데이트가 아닙니다. 도구 이름, 입력 형식, 권한 범위, 오류 처리 방식이 바뀌면 같은 프롬프트라도 다른 결과와 권한을 가질 수 있기 때문입니다.

따라서 MCP 연결도 API 통합처럼 관리하는 편이 안전합니다. 서버와 클라이언트가 사용하는 명세 버전을 기록하고, 최소 권한 토큰으로 주요 도구 호출을 테스트합니다. 업그레이드할 때는 읽기 전용 작업부터 확인하고, 이슈 생성이나 병합, 배포처럼 실제 변경을 만드는 도구에는 사람의 최종 확인을 둡니다.

출처: [GitHub Changelog: GitHub MCP Server의 다음 MCP 명세 지원](https://github.blog/changelog/2026-07-23-github-mcp-server-supports-the-next-mcp-specification/)

## 3. 모델을 바꾸기 쉽게 만들려면 실행 환경도 분리해야 한다

AWS의 7월 20일 주간 정리에는 Amazon Bedrock에서 OpenAI GPT-5.6 모델을 제공한다는 항목이 포함됐습니다. 이는 특정 모델이 “더 좋다”는 결론보다, 같은 클라우드의 보안·거버넌스·비용 관리 안에서 모델 선택지가 늘어나는 흐름으로 읽는 편이 유용합니다. 모델을 바꾸는 일은 이제 프롬프트만 바꾸는 일이 아니라 관측성, 비용 한도, 데이터 경로, 폴백 정책을 함께 검증하는 변경입니다.

모델 제공자와 실행 환경을 나누어 기록해 보세요. 애플리케이션 코드 여러 곳에 모델 이름을 직접 넣기보다 어댑터를 하나 두고, 요청·응답 형식과 실패 시 대체 경로를 테스트합니다. 모델별 토큰 사용량과 지연 시간, 도구 실패율을 비교하면 새 모델을 시험하고 문제가 있을 때 이전 모델로 돌아가기 쉽습니다.

## 이번 주의 한 줄

에이전트 시대의 배포 품질은 도구를 많이 연결하는 데 있지 않습니다. **각 도구의 권한과 버전, 문제가 생겼을 때 돌아갈 방법을 사람이 설명할 수 있어야 합니다.**
