> 2026-09-13 특별기획 · 공식 자료를 바탕으로 한 기술 해설

네트워크가 끊겨도 메모를 저장할 수 있는 앱은 안심이 된다. 그런데 브라우저의 사이트 데이터를 지우거나 기기를 바꾼 뒤에도 같은 안심을 약속할 수 있을까. 2026년 9월 13일 특별기획 네 번째 글은 로컬 저장의 장점과 책임을 함께 살펴본다.

## 브라우저 안의 데이터베이스가 주는 것

SQLite의 WebAssembly 문서는 OPFS에 데이터를 보관하는 여러 VFS를 설명하며, 성능과 여러 탭의 동시 사용 사이에 선택이 있다고 안내한다. WebKit은 OPFS를 출처에 속한 파일 저장 공간으로 설명한다. 일반적인 사용자 폴더에 파일을 만들어 두는 경험과는 다르다.

이 차이는 화면의 문구에도 영향을 준다. 로컬 트랜잭션이 완료됐을 때 표시하는 저장 완료와, 다른 기기로 복사까지 끝났다는 동기화 완료는 분리하는 편이 좋다. 둘을 같은 체크 표시로 표현하면 사용자는 실제보다 강한 보장을 기대하게 된다.

## 동기화는 데이터베이스 밖의 설계다

여행 중 식사 기록을 남기는 앱을 가정하자. 휴대전화에서는 별점을 바꾸고, 노트북에서는 같은 기록의 메모를 수정했다. 인터넷이 돌아왔을 때 어떤 값을 남길지는 로컬 SQL 실행만으로 결정되지 않는다. 수정 단위, 충돌 규칙, 삭제의 의미를 별도로 정해야 한다.

작은 서비스라면 처음부터 자동 병합을 약속할 필요가 없다. 서버 버전과 로컬 버전이 다른 항목을 보여주고 사람이 고르게 하는 방식도 출발점이 된다. 중요한 것은 마지막 응답을 무조건 덮어쓰는 일이 제품의 숨겨진 규칙이 되지 않는 것이다.

## 내보내기부터 복구를 시험한다

본고의 제안은 저장 기능을 만들 때 내보내기와 다시 가져오기를 함께 만드는 것이다. 파일이 다운로드됐다는 사실에서 끝내지 말고, 새 브라우저 환경에 가져와 내용·날짜·첨부 관계가 돌아오는지 확인해야 한다. 사진을 저장했다면 메타데이터만 복구되는 상황도 따로 검토한다.

오프라인 생성, 두 탭의 수정, 저장 실패, 사이트 데이터 삭제 후 복원을 테스트 목록에 넣자. 로컬 우선의 가치는 서버를 없애는 데만 있지 않다. 연결 상태와 무관하게 작업을 이어가면서, 데이터가 어디에 있고 무엇을 복구할 수 있는지 설명할 수 있어야 한다.
