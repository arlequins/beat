> 2026-09-13 특별기획 · 공식 자료를 바탕으로 한 기술 해설

에이전트가 문서를 찾아 요약하는 시연은 쉽게 이해된다. 같은 에이전트가 문서를 수정하고 외부에 보내기 시작하면 질문이 달라진다. 무엇을 할 수 있느냐보다, 누구의 권한으로 어디까지 실행했는지가 중요해진다. 2026년 9월 13일 특별기획 첫 편은 이 경계를 제품 기능으로 다루는 방법을 제안한다.

## 연결 성공은 실행 허가가 아니다

MCP 공식 보안 문서는 서버를 위해 발급되지 않은 토큰을 받아 하위 API로 전달하는 token passthrough를 금지한다. HTTP 인증 명세도 자원 서버와 클라이언트의 역할을 구분한다. 이 규칙이 알려주는 핵심은 연결의 편의 때문에 서로 다른 권한 경계를 합치지 말라는 것이다.

여기서부터는 제품 설계에 대한 제안이다. 검색 권한을 받았다고 파일 수정까지 허용하면 사용자는 연결 한 번으로 어떤 일이 가능해졌는지 이해하기 어렵다. 도구 목록을 이름별로 나누기보다 읽기, 초안 작성, 외부 반영처럼 결과의 성격에 따라 나누는 편이 설명하기 쉽다.

## 승인은 구체적인 변경에 묶는다

회의록에서 후속 작업을 추출하는 에이전트를 생각해 보자. 담당자 이름을 추천하는 단계와 실제 프로젝트에 작업을 생성하는 단계는 다르다. 승인 화면에는 대상 프로젝트, 생성할 작업, 담당자, 외부에 공개될 내용을 함께 보여주는 것이 좋다. 사용자가 승인한 뒤 내용이 바뀌면 이전 승인을 그대로 재사용하지 않는다.

재시도에도 같은 원칙을 적용할 수 있다. 네트워크가 끊겼다는 사실은 작업이 실패했다는 증거가 아니다. 작업 식별자를 저장하고 서버가 같은 요청을 중복 처리하지 않도록 설계해야 한다. 이것은 MCP 자체가 대신 해결해 주는 기능이 아니라, 도구를 제공하는 서비스의 책임이다.

## 출시 기준은 실패를 설명할 수 있는가

실험에서는 세 가지 상황을 먼저 만들어 보자. 읽기 전용 계정으로 쓰기 도구를 호출하고, 승인을 받은 뒤 대상을 바꾸고, 응답이 끊긴 요청을 다시 보낸다. 기대 결과는 각각 명확한 거절, 새로운 확인, 중복 없는 결과다. 로그에는 비밀 토큰 대신 요청자·대상·승인된 변경·결과를 남긴다.

좋은 자동화는 매번 사람을 부르는 시스템도, 모든 일을 조용히 끝내는 시스템도 아니다. 위험이 달라지는 지점에서만 멈추고, 이미 허용된 범위에서는 예측 가능하게 움직여야 한다. 팀이 첫 주에 정해야 할 것은 도구 개수보다 이 멈춤의 기준이다.
