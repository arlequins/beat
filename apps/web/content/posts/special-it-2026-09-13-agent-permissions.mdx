> 2026-09-13 특별기획 · 공식 자료를 바탕으로 한 기술 해설

에이전트가 문서를 찾아 요약하는 모습은 쉽게 이해된다. 하지만 문서를 고쳐 외부로 보내기 시작하면 확인할 점이 달라진다. 무엇을 할 수 있는지만큼 누구의 권한으로 어디까지 실행했는지도 중요하다. 이 글에서는 권한의 한계를 제품 기능으로 다루는 방법을 살펴본다.

## 연결 성공은 실행 허가가 아니다

MCP 공식 보안 문서는 서버에 발급되지 않은 토큰을 받아 다른 API로 전달하는 행위(token passthrough)를 금지한다. HTTP 인증 명세도 자원 서버와 클라이언트의 역할을 구분한다. 두 규칙의 핵심은 연결을 편리하게 만들려고 서로 다른 권한을 하나로 합치지 말라는 것이다.

다음은 제품 설계에 대한 제안이다. 검색 권한을 허용했다고 파일 수정까지 가능하게 하면, 사용자는 연결 한 번으로 무엇을 할 수 있게 됐는지 알기 어렵다. 도구는 이름보다 읽기, 초안 작성, 서비스에 실제 반영하기처럼 결과에 따라 나누는 편이 설명하기 쉽다.

## 실행할 변경 내역을 보여주고 승인받는다

회의록에서 후속 작업을 추출하는 에이전트를 생각해 보자. 담당자 이름을 추천하는 단계와 실제 프로젝트에 작업을 생성하는 단계는 다르다. 승인 화면에는 대상 프로젝트, 생성할 작업, 담당자, 외부에 공개될 내용을 함께 보여주는 것이 좋다. 사용자가 승인한 뒤 내용이 바뀌면 이전 승인을 그대로 재사용하지 않는다.

재시도에도 같은 원칙을 적용한다. 네트워크가 끊겼다고 해서 작업이 실패한 것은 아닐 수 있다. 작업 식별자를 저장해 서버가 같은 요청을 중복 처리하지 않도록 해야 한다. 이는 MCP가 대신 해결해 주는 기능이 아니라 도구를 제공하는 서비스의 책임이다.

## 실패했을 때 원인을 확인할 수 있는가

세 가지 상황을 시험해 본다. 읽기 전용 계정으로 쓰기 도구를 호출하고, 승인을 받은 뒤 대상을 바꾸고, 응답이 끊긴 요청을 다시 보낸다. 각각 명확히 거절되는지, 새로 승인을 요청하는지, 작업을 중복 실행하지 않는지 확인한다. 로그에는 비밀 토큰 대신 요청자와 대상, 승인한 변경, 실행 결과를 남긴다.

좋은 자동화는 매번 사람을 부르지도, 모든 일을 조용히 끝내지도 않는다. 위험이 달라지는 지점에서는 멈추고, 이미 허용된 범위에서는 예상대로 움직인다. 팀이 먼저 정할 것은 도구의 개수보다 언제 확인을 요청하고 멈출지다.
