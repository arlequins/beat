> Lumen이 리서치와 초안을 도왔습니다. 이 글은 Arlequin의 최종 검토 전인 공개 미확정본이며, 최종 판단은 Arlequin에게 있습니다.

10월 26일 기준으로 10월 20~26일의 공식 자료를 확인했습니다. 지난주에는 업데이트 준비와 의존성 검토를 다뤘습니다. 이번에는 공개된 수정 버전을 실제로 적용하는 일, 설치 시점에 패키지 요청을 통제하는 일, 짧게 유효한 인증 정보를 자동화에서 사용하는 일을 살펴봅니다. 아래의 다음 행동은 공식 발표를 바탕으로 한 Lumen의 제안입니다.

## 1. Node.js: 출시 예고에서 수정 버전 적용으로 넘어가기

지난주 예고된 보안 릴리스가 공개됐습니다. 공식 공지는 수정 버전으로 22.23.4·24.22.1·26.12.1을 안내합니다. 새로 공개된 HIGH 심각도 항목에는 Brotli 디코더의 범위 밖 쓰기 취약점인 CVE-2026-111497이 포함됩니다. 공격자가 제공한 Brotli 데이터를 애플리케이션이 `node:zlib`로 압축 해제하는 경우 메모리 손상과 원격 코드 실행으로 이어질 수 있으며, 공지는 22.x·24.x·26.x가 영향을 받는다고 설명합니다.

이제 업데이트 담당자를 정하는 데서 더 나아가, 각 배포 산출물이 수정 버전을 포함하는지 확인할 차례입니다. 컨테이너를 다시 빌드하고 실제 실행 프로세스의 버전을 확인한 뒤, 외부 응답이나 업로드를 압축 해제하는 경로의 정상·실패 동작을 검사하는 편을 제안합니다. Brotli 사용 여부만으로 이번 보안 릴리스 전체의 적용 필요성을 판단하지 말고, 공지의 다른 수정 항목도 함께 확인하세요. 관리형 런타임은 제공자의 패치 공급 상태를 별도로 확인해야 합니다.

## 2. GitHub 패키지 방화벽: 설치 요청이 통과하는 경로를 먼저 확인하기

GitHub는 10월 20일 패키지 방화벽을 공개 미리보기로 발표했습니다. 패키지 메타데이터와 다운로드 요청을 검사하며, 현재는 npm 패키지만 지원합니다. 대상은 데이터 레지던시 환경을 포함한 GitHub Enterprise Cloud 고객입니다. 관리자는 대기 기간, 보안 권고 확인 등의 정책을 정할 수 있습니다. 미리보기는 무료이며, 일반 제공 시에는 사용량에 따른 과금이 예정돼 있습니다.

개발팀에는 CI 작업 하나에서 설치 경로를 확인하는 시범 적용을 제안합니다. 정상 패키지 설치, 정책으로 차단된 요청, 예외 신청, 캐시를 쓰는 재실행을 각각 확인하고 누가 예외를 판단할지 정하세요. 지난주의 워크플로 잠금 파일이 실행할 커밋을 기록하는 기능이었다면, 이번 방화벽은 패키지를 가져오는 시점의 정책 검사입니다. 실제 요청이 방화벽을 통과하도록 설정해야 하므로 도입 선언만으로 모든 개발 장비와 CI가 보호된다고 가정해서는 안 됩니다.

## 3. GitHub CLI 만료형 토큰: 한 번 복사한 토큰에 의존하는 스크립트 찾기

GitHub는 10월 21일 CLI의 만료·자동 갱신 OAuth 자격 증명을 공개 미리보기로 발표했습니다. CLI 2.103.0부터 `gh auth login --expiring`으로 선택할 수 있으며, CLI가 만료형 접근 토큰과 회전하는 갱신 토큰을 관리합니다. 기존 로그인과 직접 제공한 토큰은 그대로 동작합니다. 원문은 토큰을 한 번 얻어 보관하는 스크립트가 만료 후 실패할 수 있다고 안내합니다.

다음 행동은 팀의 인증 방식을 일괄 변경하는 것보다 토큰을 복사·저장하는 지점을 찾는 것입니다. CLI 내부 호출, HTTPS Git 인증, 별도 도구에 넘기는 인증 정보를 나눠 점검하세요. HTTPS Git에는 공식 안내의 CLI credential helper 설정과 Git 버전 조건을 확인하고, 장시간 작업은 토큰 만료 뒤에도 인증을 갱신할 수 있는지 시험하는 방식을 제안합니다. 만료 시 재시도가 외부 작업을 중복 실행하지 않는지도 확인합니다. 이 기능은 선택 사항이며 기존 자동화에 자동 적용됐다는 뜻은 아닙니다.
