이번 주의 공통점은 자동화가 더 빠르게 실행되는 만큼, 개발팀이 **멈춤·교체·관찰의 절차**를 코드와 운영 규칙으로 남겨야 한다는 데 있습니다. 새 기능 자체보다 중요한 것은 이상 징후가 생겼을 때 누가 무엇을 검토하고, 어떤 구성 요소를 언제 바꿀지 분명히 하는 일입니다.

## 1. CI 방어는 워크플로 실행 전에도 시작된다

GitHub는 공개 저장소에서 잠재적으로 악성으로 식별한 GitHub Actions 워크플로 실행을 자동으로 보류하고, 쓰기 권한이 있는 협력자의 인증된 웹 세션 승인을 받은 뒤에만 계속 실행한다고 안내했습니다. 이는 모든 위험을 자동으로 판정한다는 뜻이 아니라, CI 자격 증명을 노리는 워크플로 변경에 사람의 검토 지점을 하나 더 둔다는 의미입니다.

개발팀은 이 보호 기능을 자체 검토 절차의 대체재가 아니라 마지막 안전망으로 다루는 편이 좋습니다. 워크플로 변경에는 코드 리뷰를 요구하고, 액션은 커밋 SHA로 고정하며, 배포 권한은 환경 승인과 최소 권한 OIDC 역할로 분리하세요. 보류된 실행이 생겼을 때는 단순 승인 대신 변경한 YAML·호출 액션·필요한 토큰 범위를 함께 확인하는 짧은 대응 절차를 문서화하면 됩니다.

출처: [GitHub Changelog: 잠재적으로 악성인 워크플로 실행 보류](https://github.blog/changelog/2026-07-28-github-actions-holds-potentially-malicious-workflows-for-approval/)

## 2. 서비스 종료 공지는 의존성 목록을 시험하는 이벤트다

AWS는 여러 서비스와 기능의 신규 고객 접근 제한, 유지보수 전환, 지원 종료 일정을 공지했고, 그중 AWS IoT Device Defender – Detect는 2026년 8월 31일부터 신규 고객이 사용할 수 없다고 밝혔습니다. 이런 공지는 특정 서비스를 쓰는 팀만의 소식이 아닙니다. SDK, IaC 모듈, 운영 런북에 직접·간접으로 묶인 서비스가 실제로 무엇인지 확인할 계기입니다.

이번 주에는 프로덕션 계정과 코드 저장소를 기준으로 서비스 의존성 목록을 한 번 대조해 보세요. 각 의존성에 담당자, 대체안, 전환 마감일, 되돌림 계획을 붙이고, 사용하지 않는 기능은 제거 후보로 분류합니다. 그 결과를 분기별 아키텍처 검토가 아니라 릴리스 체크리스트의 한 항목으로 만들면, 수명주기 변화가 긴급 장애가 되기 전에 처리할 수 있습니다.

출처: [AWS: 서비스 가용성 변경 공지](https://aws.amazon.com/about-aws/whats-new/2026/06/aws-service-availability/)

## 3. 오래 일하는 에이전트에는 진행률과 취소 경로가 필요하다

OpenAI의 6월 연구 공개는 Codex 사용자가 사람 기준 한 시간을 넘는 작업을 점점 더 많이 맡기며, 장기 실행 작업과 도구 호출이 에이전트형 작업의 특성이 된다고 설명합니다. 이 수치는 특정 제품의 성과 지표이지만, 개발자가 가져갈 실무 신호는 분명합니다. 요청 하나가 길어질수록 단일 HTTP 응답이나 성공·실패 두 상태만으로는 제품을 운영하기 어렵습니다.

따라서 장기 에이전트 작업에는 작업 ID, 단계별 상태, 구조화된 실행 로그, 시간·비용 한도, 그리고 사용자가 이해할 수 있는 취소와 재시도 경로를 설계하세요. 외부 도구를 호출한다면 부작용이 있는 단계의 멱등성 키와 승인 지점도 별도로 둬야 합니다. 먼저 한 개의 실제 워크플로에 이 관측성 계약을 적용해 보면, 모델 교체나 프롬프트 개선보다 먼저 드러나는 운영 공백을 찾을 수 있습니다.
