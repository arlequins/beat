> 2026-09-13 특별기획 · 공식 자료를 바탕으로 한 기술 해설

첫 화면이 빨리 나타나도 버튼이 먹통처럼 보이면 앱은 느리게 느껴진다. 반대로 처리 시간이 조금 길어도 입력을 받았다는 사실이 바로 보이면 기다림의 성격이 달라진다. 2026년 9월 13일 특별기획 마지막 글은 로딩 점수에서 사용 중의 반응성으로 시선을 옮긴다.

## INP가 보는 시간과 보지 않는 시간

web.dev는 INP를 클릭·탭·키보드 상호작용에서 다음 화면 갱신까지의 반응성을 평가하는 지표로 설명한다. 여기에는 입력 지연, 이벤트 처리, 다음 페인트까지의 시간이 포함된다. 서버 작업 전체의 완료 시간을 그대로 뜻하는 수치는 아니다.

따라서 주문 버튼의 INP가 좋다고 결제가 빠르다고 단정할 수 없다. 사용자는 버튼의 반응과 실제 완료를 모두 경험한다. 본고에서는 입력을 받아들였음을 보여주는 시점과 작업 완료 시점을 별도로 기록하는 방법을 제안한다. 두 시간을 분리해야 개선 대상도 명확해진다.

## 먼저 반응하고 무거운 일은 나눈다

예를 들어 긴 목록을 필터링하는 화면에서, 클릭 직후 대량의 계산과 DOM 갱신을 한꺼번에 수행하면 다음 화면이 늦어진다. 공식 최적화 가이드는 긴 작업과 메인 스레드 경쟁을 줄이는 방향을 설명한다. 다만 무조건 모든 처리를 Worker로 옮기는 것이 정답은 아니다.

작은 팀이라면 먼저 느린 동작 하나를 재현하고 실행 시간을 살펴보자. 선택된 필터의 표시, 목록 계산, 결과 렌더링 중 무엇이 오래 걸리는지 나눈다. 결과가 늦어져도 사용자가 취소하거나 다른 조건을 선택할 수 있어야 한다. 이전 요청의 결과가 늦게 돌아와 새 화면을 덮는 문제도 함께 점검한다.

## 실험실의 빠름을 사용자에게 확인한다

성능 예산은 한 번의 최고 점수보다 반복 가능한 사용자 행동에 붙이는 편이 유용하다. 검색어 입력, 결과 펼치기, 다음 페이지 이동 같은 흐름을 정하고 저성능 기기에서도 확인하자. 실제 사용에서 수집한 지표는 실험실 재현으로 원인을 찾고, 수정 후 다시 관찰하는 데 연결한다.

여기서 제안하는 완료 기준은 단순하다. 입력을 받았는지 즉시 알 수 있고, 기다리는 동안 중복 실행을 유도하지 않으며, 취소와 실패가 설명돼야 한다. 반응성은 수치를 낮추는 작업이면서 동시에 사용자가 앱을 믿고 조작할 수 있게 만드는 설계다.
