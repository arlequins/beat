화면이 빨리 떠도 버튼이 반응하지 않으면 앱은 느리게 느껴진다. 반대로 작업에 시간이 걸리더라도 입력을 받았다는 표시가 바로 나오면 기다리는 경험이 달라진다. 이 글에서는 첫 화면의 로딩 점수에서 실제 사용 중의 반응성으로 살펴볼 범위를 넓힌다.

## INP만으로는 작업 완료 시간을 알 수 없다

web.dev는 INP를 클릭이나 탭, 키보드 입력부터 다음 화면이 그려질 때까지의 반응을 평가하는 지표로 설명한다. 여기에는 입력 지연과 이벤트 처리, 다음 화면을 그리는 데 걸리는 시간이 포함된다. 서버 작업 전체가 끝날 때까지의 시간을 뜻하지는 않는다.

따라서 주문 버튼의 INP가 좋다고 해서 결제도 빠르다고 단정할 수 없다. 사용자는 버튼의 반응과 결제가 완료되는 순간을 모두 경험한다. 입력을 받았다는 표시가 나온 시점과 작업이 끝난 시점을 따로 기록하면 어느 부분을 개선해야 할지 알 수 있다.

## 먼저 반응하고 무거운 일은 나눈다

긴 목록을 필터링하는 화면에서 클릭 직후 계산과 DOM 갱신을 한꺼번에 많이 하면 다음 화면이 늦어진다. 공식 최적화 가이드는 오래 걸리는 작업을 나누고 메인 스레드가 막히지 않게 하는 방법을 설명한다. 그렇다고 모든 처리를 Worker로 옮기는 것이 정답은 아니다.

먼저 느린 동작 하나를 재현해 실행 시간을 살펴본다. 선택한 필터를 화면에 표시하는 일과 목록 계산, 결과 그리기 중 무엇이 오래 걸리는지 나눈다. 결과를 기다리는 동안에도 사용자가 취소하거나 다른 조건을 선택할 수 있어야 한다. 이전 요청의 결과가 늦게 도착해 새 화면을 덮지 않는지도 확인한다.

## 실험 환경에서 빠른 동작이 실제 사용자에게도 빠른지 확인한다

성능 예산은 한 번 얻은 최고 점수보다 반복해서 측정할 수 있는 사용자 행동에 맞춰 정하는 편이 유용하다. 검색어 입력이나 결과 펼치기, 다음 페이지 이동 같은 흐름을 정해 성능이 낮은 기기에서도 확인한다. 실제 사용 중 수집한 지표를 실험 환경에서 재현해 원인을 찾고, 수정한 뒤 다시 측정한다.

완료 기준은 단순하다. 사용자가 입력이 접수됐다는 사실을 바로 알 수 있고, 기다리는 동안 같은 작업을 반복하지 않게 해야 한다. 취소와 실패 이유도 알려야 한다. 반응성을 개선하는 일은 측정값을 낮추는 데 그치지 않고, 사용자가 앱을 믿고 조작할 수 있게 만드는 과정이다.
