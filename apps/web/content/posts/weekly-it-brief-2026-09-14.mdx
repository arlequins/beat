이번 주 소식은 기능이 늘었다는 것보다 **변화가 더 자주 찾아온다**는 점에서 맞닿아 있습니다. 브라우저 정식 버전은 더 자주 출시되고, CI에서는 러너 지원 종료 시점과 권한을 확인할 수 있게 됐습니다. 상시 에이전트는 사람이 자리를 비운 동안에도 작업을 수행합니다. 따라서 도입 여부를 정할 때는 단순히 실행할 수 있는지뿐 아니라, 변경을 알아차리고 필요할 때 멈출 수 있는지도 살펴야 합니다.

## 1. Chrome 153: 2주 출시 주기에 맞춰 회귀 테스트하기

Chrome은 9월 8일 Chrome 153부터 데스크톱·Android·iOS의 안정판을 4주가 아닌 2주 주기로 제공하기 시작했고, Chrome 154 Beta는 9월 22일 안정판 출시를 앞두고 이미 시험할 수 있다고 안내했습니다. Extended Stable은 주요 기능 업데이트를 8주 주기로 유지하지만, 일반 안정판의 변화 간격은 절반으로 줄었습니다. 기능 하나의 영향 범위가 작아질 수는 있어도, 배포 뒤에 호환성 문제를 알아차릴 수 있는 시간도 함께 짧아집니다.

브라우저 버전을 지원 목록에만 적어두지 말고 CI에서도 확인합니다. 정식 버전이 바뀔 때마다 핵심 사용자 흐름을 Stable과 Beta에서 실행하고, 새로 발생한 실패는 브라우저 버전과 기능 플래그, 재현 주소와 함께 기록합니다. Extended Stable을 사용하는 고객이 있다면 8주 업데이트 일정도 별도 캘린더에 적어, 일반 채널과 실제 관리 환경의 적용 시점을 구분합니다.

출처: [Chrome for Developers: 2주 릴리스 주기 시작](https://developer.chrome.com/blog/chrome-two-week-start), [Chrome for Developers: Chrome 154 Beta](https://developer.chrome.com/blog/chrome-154-beta)

## 2. GitHub Actions: 러너 지원 종료와 권한을 워크플로에서 확인하기

GitHub는 9월 초 Actions에 특정 러너 버전의 등록·런타임 지원 종료 시점을 조회하는 REST API를 추가했습니다. 동시에 `GITHUB_TOKEN`에 Dependabot 경보를 읽기 전용으로 부여할 수 있는 `vulnerability-alerts` 권한과, 재사용 워크플로가 실제 정의 파일의 ref·SHA·저장소·경로를 알 수 있는 `job` 컨텍스트도 공개했습니다. 이는 "워크플로가 성공했다"는 한 줄보다, **무엇이 어느 정의에서 어떤 권한으로 실행됐는지**를 더 잘 확인할 수 있게 하는 변화입니다.

먼저 사용 중인 러너 이미지와 자체 호스팅 러너 버전을 목록으로 만들고, 지원 종료 API를 월간 점검이나 알림에 연결합니다. 보안 점검 워크플로에는 필요한 경우에만 `vulnerability-alerts: read` 권한을 주고, 재사용 워크플로의 배포·감사 로그에는 `job.workflow_sha`와 `job.workflow_file_path`를 남깁니다. 누가 어떤 워크플로를 어떤 권한으로 실행했는지 기록해 두면 사고가 났을 때 원인을 찾기 쉽습니다.

출처: [GitHub Changelog: GitHub Actions 2026년 9월 초 업데이트](https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/), [GitHub Docs: 워크플로 문법의 permissions](https://docs.github.com/actions/writing-workflows/workflow-syntax-for-github-actions#permissions), [GitHub Docs: job 컨텍스트](https://docs.github.com/actions/learn-github-actions/contexts#job-context)

## 3. AWS Quick: 상시 에이전트의 권한과 결과를 관리하기

AWS는 9월 9일 Amazon Quick에 예약 작업과 모니터링 에이전트를 추가해, 노트북이 닫혀 있어도 클라우드에서 실행하고 활동 피드로 결과를 전달할 수 있게 했습니다. 사용자별 권한, 모바일 기기 관리, Microsoft Purview DLP 연동, 파일·에이전트·스킬 공유와 설치 목록도 함께 소개했습니다. 이 조합은 에이전트 자체의 품질보다 결과가 **누구에게, 어떤 권한으로, 어느 채널에 남는지**가 제품 운영의 일부가 됨을 보여 줍니다.

예약 작업마다 담당자와 접근할 데이터 범위, 결과를 받을 사람, 보관 기간, 실패 알림을 정리합니다. 처음에는 읽기 전용 자료와 제한된 수신자부터 시작하고, 실제 조직 계정에서 결과 피드의 검색·공유 범위와 DLP 정책을 확인합니다. 알림이 너무 많으면 중요한 실패를 놓칠 수 있으므로 정상 완료보다 실패와 권한 거부, 예상하지 못한 데이터 접근에 우선순위를 둡니다.

출처: [AWS: Amazon Quick의 상시 에이전트·기업 제어 기능](https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-quick-always-on-agents-sharper-feed-enterprise-controls/), [AWS: Amazon Quick](https://aws.amazon.com/quick/)
